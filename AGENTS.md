# Story Computing Machine

This repository exists to turn `[WP]` prompts into memorable short stories. The story is the product. Use tools, agents, art, and continuity only when they help the story or protect a real boundary. Give writers room to discover a better story than their first plan.

For a reader-facing introduction, see [README.md](README.md). [stories/README.md](stories/README.md) explains current story packages and older bundles; [universe/README.md](universe/README.md) locates shared facts and guidance. This file governs permissions and working practice.

## Authority and permission

- Preserve the user's request verbatim in `prompt.md`, including later user directions without overwriting the original. It controls what the story must deliver, including the intended experience. Separate explicit requirements from editorial interpretations. An outline or an agent's preference does not override it.
- Read [universe/README.md](universe/README.md) when using shared facts. `universe/` alone establishes them: `LOCKED` outranks `CANON`, and `PROVISIONAL` is guidance. A story, image, review, or editorial note does not silently add canon. Ask the user to resolve a conflict with an established fact; record an approved retcon in `universe/retcons.md`.
- [universe/style-guide.md](universe/style-guide.md) holds the few shared narrative and content boundaries. Its craft advice guides new work; it does not reopen finished stories. A deliberate prompt or story voice can depart from a default unless a `LOCKED` boundary says otherwise.
- For a named existing story, read its canon marker before making a content edit: `story.md` frontmatter in current packages, `story.json` in bundles. If the marker is missing or unclear, ask. `canon: true` locks every file in that story package until the user explicitly unlocks that named story. An explicit unlock changes only the authoritative marker in its own commit; put the user's request in that commit message. Complete that commit before any separately authorized prose or art edit. Do not infer an unlock from a critique or a general wish to improve the collection.
- New stories start with `canon: false`. Promotion needs the user's explicit approval for that named story. Check the finished prose against current universe authority, add only facts the user approves as shared, then set the marker to `true`. Promotion does not follow automatically from a good review. Unlocking a story never demotes or erases `LOCKED` or `CANON` universe facts; changing those needs its own user ruling.

## Working area and story files

Use Codex's built-in worktree workflow and continue in the worktree attached to the current chat. An existing Codex worktree needs no additional checkout or update from `main` before story production. Do all story reads for production, edits, commits, and pull-request work there. Keep the absolute worktree path in agent assignments. Use a pull request for merging and never merge on the user's behalf. Preserve authored work when changing layouts or retiring tools.

Keep all task-created files inside the active repository worktree. Use `<worktree>/tmp/` for every temporary file or directory: review inputs and outputs, scratch scripts, logs, pull-request body files, and draft or rejected art. Only `tmp/.gitkeep` is tracked; everything else under `tmp/` is ignored. Derive the absolute worktree root with `git rev-parse --show-toplevel`, pass an explicit directory to temporary-file APIs, and set `TMPDIR`, `TMP`, and `TEMP` to that root's `tmp/` in subprocess environments when needed. Do not use the system temporary directory, a sibling worktree, or a location outside the repository for task files, and do not follow a symlink or junction out of the worktree to write them.

Codex manages the session's permissions; story production does not require a particular sandbox profile or reopening the chat. Read-only access to external inputs remains allowed. Git and agent applications manage their own metadata; the worktree rule above governs the task files agents create. The former repository write hook is removed; these working-area instructions still apply.

For a new story, keep `stories/<slug>/` small:

- `prompt.md` — the exact request, explicit constraints, and display names of any supplied reference images. Keep the original image files, under their recorded names, in `art/references/` beside this story. Inspect every supplied original, and ask for reattachment if one is inaccessible. These inputs are not canon authority.
- `outline.md` — begin with a short statement of the promised experience: distinctive pleasure, tone, scale, central relationship, and anticipated payoff, including later user directions. Distinguish explicit requirements from interpretations, then identify concrete scenes that could deliver those promises. The direction remains short and provisional; it can be paragraphs, beats, or a scene sketch and does not bind the finished story.
- `story.md` — the reader-facing story, with `title`, `created`, and `canon: false` frontmatter.
- `notes.md` — concise editorial memory in the spirit of the one-paragraph template. Preserve the reader effects, reasoning, repairs, and any useful dissent without making a scorecard or transcript.
- `ratings.md` — the required AO3-style rating (General, Teen, Mature, or Explicit) assigned after the prose and any cover are finalized, with a brief reason and specific content notes. Use the template's explicit `- **Rating:** General` field (with the reviewed rating in place of General) so readers and importers can identify it consistently. General is the starting target for a new story without a requested audience, not an automatic final classification. It describes content intensity, not narrative ambition or scale.
- Character reference sheets and location reference paintings come first in the art workflow for a new `[WP]` story, after its prose is ready, unless the user asks for prose only. Make a separate sheet on a plain white background for each principal character and paintings of the distinct locations important to the finished story. Exactly one character belongs on each sheet: its multiple views, poses, expressions, and useful clothing or props. Do not combine distinct characters into group or ensemble sheets. A multi-headed creature still counts as one character. A story with multiple important settings needs multiple location references, at least two distinct places; alternate views or corrections of one place do not count. A story confined to one setting needs only that location; do not invent places to meet a quota. Choose reference subjects and details from the prose and supplied originals before choosing the cover scene. A sheet shows a consistent character across its studies; label the character and story. A standalone portrait is optional art, not a substitute for the sheet. Keep accepted character art in `art/characters/` and location art in `art/landscapes/` or `art/interiors/`. Inspect the actual pixels against the story and any supplied originals.
- `title-image.jpg` — make the cover only after the character and location references are complete and inspected, using the relevant accepted references to keep it consistent. Keep accepted final art under descriptive character or location names. Do not create paired “Original” and “Selected” location images or a new `art/selection-notes.json`; corrections replace candidates rather than becoming duplicate package assets. Drafts, superseded candidates, and rejected images belong under the worktree's `tmp/`; Git history preserves revisions to previously committed art. Preserve supplied originals in `art/references/`.

Older four-file current packages and `05-story.md` bundles may stay as they are. Their old reviews, profiles, and extra historical files are records, not instructions to recreate the retired process. For an authorized edit, preserve the layout and scope; use `notes.md` for new editorial decisions without rewriting old `review.md`. Git commits for the first complete draft and each substantial revision preserve the actual prose changes; `notes.md` preserves the reasoning even if a pull request is squash-merged. No hashes, PASS tokens, or generated process records are needed.

Read a bundle's `README.md` for its historical file map, then use [stories/README.md](stories/README.md) for current file roles. Its `story.json` is authoritative for current canon status even when the historical README records an earlier status.

## The editorial work

Use [story-create](.agents/skills/story-create/SKILL.md) for a new `[WP]` story or a substantial authorized revision. Assess prompt fulfillment before choosing a plot, before drafting, and throughout revision. Literal inclusion of requested details does not establish that the story delivers the requested experience. The workflow centers on a writer, an independent challenge to the provisional outline, cold readings of the draft, and fresh whole-story readings after revision.

For a new story, assign the existing Codex outline reader as a continuing promise keeper before plot selection. In a fresh assignment, it reads only the complete user request and any relevant supplied originals, then records its own understanding before seeing the outline, the coordinator's interpretation, or other editorial framing. Preserve a short attributed account in `notes.md`, separating explicit requirements from inferred pleasures. It then joins the existing outline discussion and follows the story through drafting and revision, reading later user directions independently before editorial framing. For a substantial authorized revision, use the same independent request reading before exposing the proposed revision. The keeper is not an extra review panel and cannot serve as a cold prose reader; preserve genuinely cold draft readers and fresh final readers.

The keeper checks whether the distinctive premise drives events, revelations change what can happen or what characters can choose, and the ending delivers the promised experience. When grandeur is requested, powerful characters must exercise consequential power. A brief spectacle followed by an unrelated modest resolution can still miss the promise. Resolve material mismatches in the outline or story structure before polishing; better dialogue, clearer mechanics, or household-task symbolism cannot supply a missing experience.

Give writers and readers the complete request, including later user directions. Do not narrow assignments with unsupported instructions such as “keep the stakes small” or “avoid a major conflict.” Writers and keepers should challenge such directions against the user's words. Judge familiar tropes by whether they deliver satisfying, specific results, rather than rejecting an “obvious” solution for being familiar. A story need not invent a public crisis; equally, do not suppress adventure, conflict, spectacle, or grandeur when the request calls for them. Notice recurring collection defaults, especially extraordinary premises reduced to humble work, therapeutic conversations, or maintenance, without forcing spectacle or artificial novelty onto every story.

Each finding becomes a conversation with the writer, not a score or automatic veto. The coordinator must answer evidence-based promise objections with reference to the request and the text, distinguish requirements from interpretations, and record a concise reason for the decision. Majority approval cannot override an explicit user requirement. Examine inferred promises on their merits without turning the keeper's interpretation into authority. Check relevant canon, names, and internal consistency throughout production as needed and again before handoff.

For required Claude readings, use the authenticated `claude.ai` subscription session, not API-key billing. Check `claude auth status` with inherited `ANTHROPIC_API_KEY` removed from the Claude subprocess environment; confirm `authMethod: claude.ai` and an active `subscriptionType` before the first read. An API credit error is a reason to correct authentication and retry, not grounds to skip Claude or substitute a reader.

For a new `[WP]` story, round-robin discussion of both the outline and the final whole-story reading is required, not optional. After independent first reads, relay each participant's actual findings to the writer, Codex reader, and Claude; include the continuing keeper's findings after cold first reads are delivered. Let them answer and challenge one another, then judge the evidence in the text. Parallel reviews, a coordinator summary, or a vote do not replace that exchange. Do not call either stage complete while a material objection remains unexamined or an explicit requirement remains unmet. Outlines remain provisional; repairs to minor wording do not restart every review stage. Use contextual checks for local changes and whole-story readings for substantial revisions, with fresh readers after structural reworking as the skill specifies.

A localized edit should remain local unless reading exposes a structural problem that the user has authorized fixing. For a localized prose change that alters meaning, action, or voice, have one independent reader read the changed passage in the context of the whole story and record the useful finding in `notes.md`; the coordinator rereads a purely mechanical correction. Only an explicit request to replace or remake one named non-canon story triggers clean replacement; other authorized revisions stay in place and retain the package. For replacement, preserve the user's original request, reference inventory, and original files from `art/references/`, and let the coordinator read earlier notes to understand what failed. Remove the named package before clean creation, including its old prose, notes, outline, review, cover, and generated art; restore the preserved originals in the new package. Do not use the old prose or generated art as a template. If an illustrated or graphic-novel edition of the old story exists, tell the user it remains tied to the previous prose and leave it intact. Carry useful diagnosis into fresh notes. Git history retains the former work.

Make art after the prose is strong. For a new `[WP]` story, finish and inspect the principal characters' reference sheets and references for the story's important locations first, then make and inspect the cover, all before the final rating and pull request unless the user requested prose only. The cover uses the references; it does not determine which characters or places receive them. Each image must match the finished story and any supplied reference; inspect its actual pixels, including identity consistency and readable labels on the sheets. There is no mandatory gallery inventory or fixed number of extra images beyond the reference coverage above. Existing story art is a creative asset, not canon. Do not add files to a locked package without an explicit user ruling. The user's one-time approval to relocate pre-lock art into canon story directories in PR #358 did not unlock those packages or authorize later art changes.

AO3 rating is a required final production step for a new `[WP]` story. Complete the final whole-story discussion and resulting prose revisions first; then finish and inspect the cover if one is included. Rate the finished prose and selected cover together under [universe/style-guide.md](universe/style-guide.md), or the prose alone when the user requested prose only. Record the classification, brief reason, and specific content notes in `ratings.md` before opening the draft pull request. Reassess the rating if the prose or cover changes afterward. For a substantial authorized revision of an existing story, review its rating after the revised work is final and update it if needed, while preserving the package's authorized layout.

[universe/art.md](universe/art.md) preserves the collection's visual direction and art provenance guidance. It guides authorized new art without establishing in-world facts.

`illustrated/` and `graphic-novels/` contain existing editions. Keep them as authored artifacts; neither changes the source story or establishes canon. The former site and page-publication processes are retired. The separate `media/` CI workflow exports selected final art to R2 for downstream use; it does not publish story pages. Any new edition or page-publication method is a separate, explicit project.
